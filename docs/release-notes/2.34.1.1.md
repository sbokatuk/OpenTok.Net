# OpenTok.Net 2.34.1.1

The first release of this repository as a cross-platform API rather than a repackaging of the two
platform bindings, and the first on Vonage's OpenTok SDK **2.34.1** on both platforms.

Two packages now:

| Package | What it is |
| --- | --- |
| `OpenTok.Net` | `OpenTokSession`, `OpenTokPublisher`, `OpenTokSubscriber` — one API over both native SDKs. No MAUI dependency. |
| `OpenTok.Net.Maui` | `OpenTokVideoView` and its handlers, plus `UseOpenTok()`. New package. |

```csharp
using var session = new OpenTokSession(apiKey, sessionId);

session.Connected      += (_, _) => session.Publish(publisher);
session.StreamReceived += (_, e) =>
{
    var subscriber = new OpenTokSubscriber(e.Stream);
    RemoteView.Source = subscriber;
    session.Subscribe(subscriber);
};

session.Connect(token);
```

No `#if IOS`, no `#if ANDROID`, no delegate subclass, no Java listener, no `JavaCast`, and no
hand-written video-view handler.

## Breaking: the old `OpenTok.Net` package was something else

`2.27.1.817` and earlier were a *fat* package: both platform bindings' `lib/` and `native/` trees
unzipped and re-zipped into one nuspec, with an MSBuild target that copied `native/` into
`lib/<tfm>` on the consumer's first build to make up for the binding SDK's own native-reference
packaging being lost in the process.

Upgrading keeps everything working — `OpenTok.Net` still brings the right platform binding in per
target framework, so `OTSession` and `Com.Opentok.Android.Session` remain available exactly as
before — but it does so through an ordinary conditional `PackageReference` rather than the copy
step. Code written against the raw bindings needs no changes. Code that relied on the `native/`
directory layout inside the package does.

The platform bindings themselves moved to their own repositories some time ago, and both had
breaking changes of their own in this generation — see
[`OpenTok.Net.iOS 2.34.1.1`](https://github.com/sbokatuk/OpenTok.Net.iOS/releases) in particular,
which raises the iOS floor and renames several delegate and enum members.

## Requirements

- **iOS 15.0+** — OTXCFramework 2.34.1's own floor, raised from 13.0 by that SDK release.
- **Android API 24+** — `opentok-android-sdk`'s own `minSdkVersion`.
- **JDK 17+** on `$JAVA_HOME` for any Android app build.

Six target frameworks per package: `net8.0`, `net9.0` and `net10.0`, for iOS and Android.

## What the façade does and does not hide

Hidden, because it is accidental rather than real: iOS answering an `OTError` out parameter where
Android returns void and reports through a listener; a delegate object per protocol versus a
listener interface or an event; `UIView` versus `Android.Views.View`; Android needing a `Context`;
`Publisher.Builder.Build()` needing a `JavaCast`.

Not hidden, deliberately: `OpenTokError.Code` is the platform's own number, because the two SDKs
number their errors differently and Vonage documents no correspondence — log it, do not branch on
it across platforms. Permissions are not requested for you, because when to ask and what to do when
refused is a UI decision.

`OpenTokConnectionState` is the intersection both platforms can answer for — iOS exposes six states,
Android exposes none and only fires callbacks — so the façade tracks it rather than asking the SDK.

## Infrastructure

This release also brings the repository up to the same standard as the two binding repositories:
CI on pull requests and tags with trusted publishing, a reusable build workflow, e2e checks on a
simulator and an emulator, package-layout tests, and repository-consistency tests.

The consistency and package tests both assert the invariant this package exists for: **both pinned
platform bindings wrap the same native SDK generation.** A mismatch is otherwise invisible — both
packages exist, both restore, everything builds and publishes, and the app simply behaves
differently on one platform.

The device tests are worth a specific mention: they contain no `#if` at all. The same calls,
compiled once, drive `OTSession` on iOS and `Com.Opentok.Android.Session` on Android, and check that
the state machine, argument validation and disposal semantics come out identical on both. Nothing
connects, publishes or subscribes, so no credentials, network or camera are involved.

## Versioning

`<native SDK version>.<façade revision>`, so `2.34.1.1` means "wraps OpenTok SDK 2.34.1". The
revision restarts at 1: nuget.org carries real `2.27.1.x` releases of this package id up to
`.817`, and `2.34.1.1` sorts above all of them.
