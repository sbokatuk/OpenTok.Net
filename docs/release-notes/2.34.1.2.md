# OpenTok.Net 2.34.1.2

Takes the façade from connect/publish/subscribe to most of what both SDKs actually do — all of it
still with no `#if IOS` or `#if ANDROID` anywhere in a consuming app.

## Added

| | |
| --- | --- |
| **Signalling** | `Signal(type, data, to)` and `SignalReceived`, with `FromSelf` computed for you |
| **Participants** | `ConnectionCreated` / `ConnectionDestroyed` and `OpenTokConnection` — a participant who joined but has not published |
| **Moderation** | `ForceMuteAll`, `ForceMuteStream`, `DisableForceMute`, `ForceDisconnect`, `MuteForced`, and `Capabilities` |
| **Reconnection** | `Reconnecting` / `Reconnected` |
| **Archiving** | `ArchiveStarted` / `ArchiveStopped` |
| **Encryption** | `SetEncryptionSecret` |
| **Camera** | `CameraPosition`, `SwapCamera()`, `CameraTorch`, `CameraZoomFactor` |
| **Audio levels** | `AudioLevel` on both publisher and subscriber |
| **Captions** | `SubscribeToCaptions`, `CaptionsTranslationLanguage`, `Caption` |
| **Volume** | `AudioVolume` per subscriber |
| **Transformers** | `OpenTokTransformer` with `BackgroundBlur`, `BackgroundReplacement`, `NoiseSuppression`, plus `SetVideoTransformers` / `SetAudioTransformers` |

Three of these were worth more than a line of plumbing each:

- **`FromSelf`.** Both SDKs deliver a signal back to its own sender, and neither flags it. Every
  chat implementation over this API rediscovers that its messages appear twice. The façade compares
  against the session's own connection id so the app does not have to.
- **`CameraPosition`.** Android's SDK has no "use this camera" call — only `CycleCamera` — and both
  `CameraId` and `SwapCamera` are deprecated in the current version. The façade tracks the position
  and cycles only on a real change, which is the one non-deprecated route and no less accurate than
  the alternative.
- **`CaptionsTranslationLanguage`** reads back after setting, because the SDK *ignores* an
  unsupported language rather than rejecting it — so reporting the requested value would be a lie.

`OpenTokError.Code` is still deliberately not unified; see the README.

## Transformers need a separate package

`OpenTokTransformer` is in this package, but the implementations are not: they live in
`OpenTok.Net.Transformers.iOS` / `OpenTok.Net.Transformers.Android`, which are **not** dependencies
of anything here because each costs around 70 MB. Without one, the SDK reports that the transformers
library is not loaded — at runtime, from a call that compiled and linked.

The sample deliberately does not reference them either, so its Blur and Suppress noise buttons
demonstrate both the API and that failure. Adding either package to the sample's `.csproj` makes
them work.

## Sample

`samples/OpenTok.Sample.Maui` now exercises every row of the table above in one page: multiparty
(a view per remote stream, not just the first), text chat over signalling, camera controls with a
zoom slider, audio-level meters, captions, and the transformer buttons — with no per-platform code.

## Calling services: CallKit and `android.telecom`

`OpenTokAudioSession` — four methods, and the whole SDK-side handshake for both platforms:

```csharp
OpenTokAudioSession.EnableCallingServicesMode();   // once, at launch
OpenTokAudioSession.PrepareForCall();              // on answer
OpenTokAudioSession.NotifyActivated();             // from the OS callback
OpenTokAudioSession.NotifyDeactivated();
```

It is genuinely symmetric rather than an invented shape. iOS has `OTAudioSessionManager`
(`enableCallingServicesMode`, `audioSessionDidActivate:`, `audioSessionDidDeactivate:`); Android has
`BaseAudioDevice.AudioFocusManager` (`setRequestAudioFocus(false)`, `audioFocusActivated`,
`audioFocusDeactivated`). Same three operations, same purpose: stop the SDK managing audio, because
the OS will.

Without it, the SDK and the calling framework both try to own the audio session or audio focus, and
the symptom is a call that connects with no sound.

What is deliberately **not** unified is the calling integration itself. `CXProvider` and
`ConnectionService` have nothing in common beyond their purpose — on iOS the app owns a provider
object and calls it; on Android the framework binds a service and asks the app for connections. So
they get two separate samples rather than one with an `#if`:

- **`samples/OpenTok.Sample.CallKit.iOS`** — `CXProvider`, reporting an incoming call, answering
  from the system UI, and connecting the session from `DidActivateAudioSession` rather than from
  the answer action. That ordering is the point: media must not start until CallKit says audio is
  live, and doing it on answer appears to work in the simulator and fails on a device.
- **`samples/OpenTok.Sample.Telecom.Android`** — a self-managed `PhoneAccount`, a
  `ConnectionService`, a `Connection` driving the session, and the foreground service below.

Both are triggered from a button rather than a push, because PushKit and FCM need certificates and a
server; everything downstream of the report is identical.

## Lifecycle: `Pause()` / `Resume()`

`OpenTokSession.Pause()` and `Resume()`, for backgrounding. Android's SDK expects the app to drive
this and keeps capturing otherwise; iOS handles it itself, so it is a no-op there — present on both
so lifecycle code needs no `#if`. The sample wires them to the window's `Deactivated`/`Activated`.

## The Android foreground service the samples were missing

Since Android 14 a background app is refused camera and microphone access unless a foreground
service with the matching `foregroundServiceType` is running. **Silently** — the app keeps running,
the session stays connected, and it captures nothing, which the other participant experiences as a
frozen frame and silence.

`OpenTok.Sample.Maui` now ships one (`Platforms/Android/OpenTokCaptureService.cs`), started when
publishing starts and stopped when it stops, behind a small `CaptureLifetime` shim that is a no-op
on iOS. Verified in the built APK: `foregroundServiceType=0xc0` — camera and microphone — with both
permissions merged.

This is not a telecom concern; any OpenTok Android app that can be backgrounded mid-call needs it.

## CI: Release builds now verify native linking

New `verify-release` job on pull requests, one leg per platform. A release skips it, because the
tagged commit already passed it on its own PR.

A façade is *more* exposed to the managed linker than a plain binding, not less: every path through
`OpenTok.Net` ends in a platform partial whose only caller is a delegate or listener the SDK invokes
through the Objective-C runtime or JNI — exactly the shape the linker decides is dead. Debug leaves
the linker off, so the existing sample job could only say the packages restore and compile. The iOS
leg also links for a real device (`ios-arm64`, code signing off), which nothing else here does.
